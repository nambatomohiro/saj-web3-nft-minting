## 1. 目的とスコープ

### 目的
- Part4まで追随する参加者（想定 **10〜30人**）の提出アドレスへ、**各 0.1 POL** を事前配布する。
- 当日 faucet 詰まりの根本対策（設計書§8）を、手作業ではなく**再実行に強いスクリプト**で実現する。

### スコープ外（YAGNI）
- メインネット送金・実資産の取り扱い（本ツールはAmoyテストネット専用）。
- faucet からの POL 取得自動化（faucet は手作業で日次取得。§運用手順を参照）。
- 参加者アドレスの収集フォーム自体の実装（Slack/Discord チャンネルを人力で使う）。
- 送金額の個別変更 UI（全員一律 0.1 POL 目標に固定）。

---

## 2. 運営モデル前提（設計の土台）

- 参加者は**各自セミナー専用ウォレットを新規作成**し、**アドレスのみ**を提出する（設計書§7-8、README事前準備4）。秘密鍵は誰も預からない。
- アドレス提出先は今回 **Slack/Discord のチャンネル**（Googleフォームの代わり）。
- 送金元（原資）は **実演台ウォレット `0x9f289dce99B33fa168211cC0BD382663c493c9c2` を共用**する。`.env` の `SEMINAR_PRIVATE_KEY` がそのまま原資鍵になるため、鍵の追加管理は不要。
- 実測ガス（30 gwei時）: 通し工程 deploy→mint→burn で約 0.048 POL。0.1 POL は約2倍の余裕（ガス価格上昇時でも1.5倍前後は確保）。

## 3. 全体像

既存の hardhat タスク構成（`tasks/handson.js`）に倣い、**運営専用 hardhat タスク `distribute`** を新設する。ネットワーク・署名アカウントは既存の `hardhat.config.js`（`.env` 注入）をそのまま再利用する。

```bash
# ドライラン(既定): 誰にいくら送るか・原資が足りるかを表示するだけ
docker compose exec hardhat npm run distribute:amoy -- distribute/recipients.txt

# 実送金: --execute を明示したときだけ実際に送る
docker compose exec hardhat npm run distribute:amoy -- distribute/recipients.txt --execute
```

`package.json` に `distribute:amoy` スクリプト（`hardhat --network amoy distribute`）を追加する。

## 4. コンポーネントと責務

| ユニット | 役割 | 依存 |
|---|---|---|
| `tasks/distribute.js` | `distribute` タスク本体。宛先パース→検証→原資チェック→送金ループ→サマリ | ethers（hardhat-toolbox 同梱）、`hardhat.config.js` の amoy 設定 |
| `distribute/recipients.txt` | 宛先アドレス一覧（1行1件、運営が Slack/Discord から手貼り）。**git管理外** | なし |
| `hardhat.config.js` | 既存。`require("./tasks/distribute")` を1行追加 | `.env`（`SEMINAR_PRIVATE_KEY`） |

タスク本体は次の小関数に分ける（単体で読める粒度）:
- `parseRecipients(text)` → 各行から `0x[0-9a-fA-F]{40}` を正規表現抽出。空行・重複・不正行はスキップし、警告一覧を返す。
- `planTransfers(addresses, provider, target)` → 各宛先の現残高を照会し、不足分（`target - balance`、負なら0＝スキップ）を算出。
- `checkTreasury(plan, senderBalance, reserve)` → 送金総額＋概算ガス＋実演予備（`reserve`）が原資残高に収まるか判定。
- `execute(plan, wallet)` → nonce 順に送金し、各txの confirmation を待ってリンク表示。

---

## 5. 送金ロジック（冪等 top-up 方式）

各宛先について「**現在残高を見て、目標 0.1 POL に満たない分だけ送る**」。

- 目標額 `TARGET = 0.1 POL`（タスク内の定数。将来変えるならここ1箇所）。
- 残高 ≥ TARGET の宛先は **スキップ**（二重配布防止）。
- 残高 < TARGET の宛先には `TARGET - 残高` を送る。
- **冪等性**: 途中で失敗しても、再実行すれば「まだ足りない宛先」だけに再送される。固定額送金だと再実行で二重配布になるため、top-up 方式を採用する。
- nonce は送信ごとに順に採番し、各送金の receipt（1 confirmation）を待って次へ進む（nonce 衝突・取りこぼし防止）。

---

## 6. 安全策（最重要）

1. **ドライラン既定**: 引数に `--execute` が無い限り、一切送金せず「宛先ごとの送金予定額・スキップ・総額・原資充足」の一覧だけを表示する。実送金は明示的オプトイン。
2. **原資充足チェック**: `送金総額 + 概算ガス + 実演予備(0.15 POL)` を送金元残高と比較し、**足りなければ送金前に停止**して不足額を表示する。
3. **不正宛先の可視化**: パースで弾いた行（不正・重複・空）を警告一覧として表示。件数が想定と合うか運営が目視できる。
4. **進捗ログとサマリ**: 1件ごとに `amoy.polygonscan.com` の tx リンクを表示。最後に「成功 / スキップ / 失敗」の件数サマリを出す。失敗があれば再実行を促す。
5. **宛先ファイルは git 管理外**: `distribute/` を `.gitignore` に追加。参加者アドレスは個人情報寄りのためコミットしない。

## 7. データ形式

### 入力: `distribute/recipients.txt`
1行1件。前後に日本語やラベルが混じっていてもよい（正規表現で `0x…` を抽出）。

```
0x1234...abcd
私のアドレスは 0x5678...ef01 です      # ← 抽出される
0x9abc...2345
```

### 出力（ドライラン例）
```
宛先: 24件（重複2件・不正1行をスキップ）
送金予定: 22件 / 合計 2.15 POL（うち2件は残高十分でスキップ）
原資: 3.42 POL（送金2.15 + ガス概算0.02 + 実演予備0.15 = 2.32 → OK、余裕1.10 POL）
※ 実送金するには末尾に --execute を付けて再実行してください
```

## 8. エラーハンドリング

| 事象 | 挙動 |
|---|---|
| 宛先ファイルが無い/空 | エラーメッセージを出して中断（送金しない） |
| 抽出できた有効アドレス0件 | 中断（送金しない） |
| 原資不足 | 不足額を表示して**送金前に**中断 |
| 個別送金の失敗（RPC断・nonceエラー等） | その宛先を「失敗」に記録して次へ継続。最後にサマリで再実行を促す |
| 署名アカウント無し（`.env` 未設定） | 既存の handson タスクと同じく明示エラー |

## 9. テスト方針

- `parseRecipients` の単体テスト（正常・重複・不正混在・日本語混じり）を `test/` に追加。
- 送金ループ自体は Amoy 実ネット依存のため自動テスト対象外。**当日前リハで少数の自分のアドレス（2〜3件）に対しドライラン→executeを1回通す**ことで担保する（運用手順に組み込む）。

---

## 10. 運用手順（当日まで）

1. faucet（[faucet.polygon.technology](https://faucet.polygon.technology/) 等）で実演台ウォレットを **3.5 POL 程度**まで補充（0.1×30 + 実演予備 + ガス）。日次上限があるため**数日前から**貯める。
2. アドレス提出締切後、Slack/Discord の投稿を `distribute/recipients.txt` に手貼りで集約。
3. `npm run distribute:amoy -- distribute/recipients.txt`（ドライラン）で件数・総額・原資充足を確認。
4. 自分のテストアドレス数件で一度 `--execute` を通し、動作を確認（リハ）。
5. 問題なければ本番リストで `--execute`。サマリで失敗ゼロを確認（失敗があれば再実行）。
