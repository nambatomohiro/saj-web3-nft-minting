## 1. 目的とスコープ

### 目的
- NFT発行を**手を動かして"実装体験"**する（座学の反対）。
- 会員証NFTの本質（token-gating＝保有者だけが会員）を、コードを叩いて体験する。
- 将来の「本物の会員証」（Base メインネットに Soulbound で実配布）への布石とする。

### 位置づけ ★踏み外してはいけない前提
- ここで作るのは**「練習台」**であり、**そのまま本物の会員証ではない**。
- 当日「これは練習。本物の会員証は将来 Base にソウルバウンドで刻む」と**明言**する。
- 地雷: テストネット × 譲渡自由な素の ERC-721 を「会員証」と呼んで配ると核心を踏む。「練習台」と役割を明示して回避する。

### スコープ外（YAGNI）
- 会員証の画像アセット／見た目のあるカード表示（事故要因を持ち込まない）。
- Soulbound コントラクト（本番の論点。練習台はあえて譲渡可能にして学びに使う。§4参照）。
- Base メインネットへのデプロイ、実配布 airdrop（本番イベントの範疇）。
- クラウド／ブラウザ完結の実行環境（GitHub Codespaces 等）。ローカルDocker一本。

## 2. 運営モデル（最重要の設計原則）

**「主催者の実演が保証された背骨。ハンズオンは環境を用意できる人のオプション」** というハイブリッド運営。

- **主催者（難波）の実演** = プロジェクターに映る**絶対に事故らない背骨**。これ1本でイベントが成立する。
- **ローカルでDockerを動かせる人** = 同じイメージ・同じコマンドで**追随（follow-along）**する。
- **社用PC等で動かせない人** = 前の実演を見て理解する。MetaMask も同様（実演中心、追随はできる人のみ）。

### この原則から導かれる帰結
1. **主催者の実演環境が唯一のクリティカルパス**。全員の環境をケアするのではなく、主催者1台が絶対に事故らないことに投資を集中する。
2. **実演台と追随勢の環境を一致させる**必要がある → 事前ビルド済みイメージを配布（§5）。
3. **背骨は外部依存に賭けない** → ローカルチェーン（オフライン・即確定・100%制御下）を背骨に置き、Amoy（外部テストネット）は"ごほうび層"に留める（§6）。
4. **MetaMask は必須ではなく演出** → 発行機構は `.env` の秘密鍵＋スクリプト出力＋エクスプローラで完結する。MetaMask は「見慣れたウォレットUIで見る」ための任意要素。

## 3. 体験レベル（何をどこまで触るか）

**レベルB**（発行 ＋ 会員判定）を採用。参加者が触るNFTライフサイクル:

```
mint（発行） → check-membership（会員かYES/NO＝token-gating体験） → transfer（譲渡実演） → burn（焼却）
```

- 発行して終わり（レベルA）ではなく、**「会員かどうかをコードで判定させる」**まで踏み込むことで、会員証の本質（token-gating）を手で体験する。
- 見た目のあるカード表示（レベルC）は事故要因のため入れない。

## 4. コントラクト設計

### 規格・性質
- **OpenZeppelin ERC-721** ベース。
- **譲渡可能（transferable）＋ burn可能**。**Soulbound にはしない**。
- メタデータ: Slack案どおり `{ "name": "SAJ Web3 Member", "member": "<名前>", "year": "2026" }`。まずはシンプルに（JSONベース、画像なし）。

### なぜ練習台を「譲渡可能」にするか（教育の順序）
- Part3/4 で「見て、隣の人のウォレットに自分のNFTを送れてしまう」を**実演できる**。
- そのうえで Part5 で「でも会員証がこれだと"売れてしまう"よね？ → だから本物は Soulbound にする」と、**参加者自身の体験から Soulbound の必要性に気づかせる**。
- 「制約の理由を体験する前に制約を課す」Soulbound先出しよりも、気づきの順序が自然。

### burn（焼却）
- **burn可能**にしておき、Part4 の締めで各自が Amoy 上の練習会員証を焼却する（"焼却儀式"）。
- 「これは練習だったから最後に燃やす → 本物は将来 Base に」という締めで、位置づけ（§1）と噛み合わせる。
- burn は NFTライフサイクル（mint/burn）と、本番設計での「失効（revocation）」概念の布石にもなる。

## 5. Docker 構成 ★本設計の主目的

### 方針
- **事前ビルド済みイメージをレジストリから `docker pull`**。当日その場でビルドしない。
  - 理由: 当日 wifi でのビルド待ち／npm install 失敗という事故要因を消す。実演台と追随勢の環境を一致させる。
- **コンテナ1個**。起動すると中で **Hardhat node（ローカルチェーン）** が走り続ける。
  - `docker compose up` でローカルチェーンが立ち、ログを実演で見せられる。
- **各コマンドは `docker compose exec` で叩く**。
- **重い `node_modules` はイメージに焼き込み、ソース（コントラクト/スクリプト）は git リポジトリ側**に置きボリュームマウント。
  - 起動が速く事故らない＋ Solidity コードを参加者が読める。node_modules は匿名ボリュームで保護する標準パターン。
- **秘密鍵・RPC は `.env` で実行時に渡す**（イメージに焼き込まない）。`.env.example` を用意。

### 構成要素（概略）
- `Dockerfile`: `node:20` ベース、`package*.json` を COPY → `npm ci` で node_modules を焼き込む。→ レジストリに push。
- `docker-compose.yml`:
  - `image: <registry>/saj-nft:latest`（事前ビルド済み）
  - `command: npx hardhat node`（0.0.0.0:8545 でローカルチェーン）
  - `ports: "8545:8545"`（ホストの MetaMask から localhost ネットワークとして接続可能に）
  - `env_file: .env`
  - `volumes: [".:/app", "/app/node_modules"]`（ソースはマウント、node_modules は匿名ボリュームで保護）
- `.env.example`: `SEMINAR_PRIVATE_KEY=`（各自のセミナー専用ウォレット鍵）、`AMOY_RPC_URL=`。

### 参加者導線（追随勢）
```
git clone <repo>            # 軽量（重い依存はイメージ側）
cp .env.example .env         # 秘密鍵・RPC を記入
docker compose up            # 事前 pull 済みイメージ起動 → ローカルチェーン稼働
docker compose exec hardhat npm run <script>
```

## 6. ネットワーク戦略（Part3 / Part4 の二層）

**ローカル背骨 ＋ Amoy payoff の二層**。同一コントラクト・同一スクリプトを、宛先ネットワークだけ切り替える（`--network localhost` / `--network amoy`）。

| | Part3 ローカル（Hardhat node） | Part4 Amoy（公開テストネット） |
|---|---|---|
| 役割 | **背骨**。オフライン・即確定・100%制御下・失敗しえない | **ごほうび層**。公開検証性＋本物のネットワーク感 |
| 他人から見えるか | 見えない（自PC内のみ） | `amoy.polygonscan.com` で誰でも見える |
| 残るか | コンテナ停止で消滅（練習台らしい） | 残る（テストネットなので"ソフトな永続"。定期的に廃止・リセットされうる） |
| ガス | 不要（POL無しでも体験できる） | テスト用POLが必要（§8で事前配布） |

- **Amoy一本にはしない**。外部テストネットのRPC健全性・POL配布を"背骨"に賭けると、実演が事故りうるため（運営モデル§2の原則に反する）。
- Hardhat `networks` に `localhost` と `amoy`（RPC＋`.env` の鍵）を定義。

## 7. スクリプト設計

Part3・Part4 で**同一**。`--network` の切替のみで両対応。`package.json` の npm scripts として公開。

| スクリプト | 内容 |
|---|---|
| `deploy` | 会員証コントラクトを対象ネットワークにデプロイ |
| `mint` | 自分（`.env` の鍵のアドレス）に会員証を1枚発行 |
| `check-membership <address>` | 指定アドレスが会員か判定 → YES/NO（token-gating体験。`balanceOf`/`ownerOf`） |
| `transfer <to>` | 自分の会員証を指定アドレスへ譲渡（"送れてしまう"実演） |
| `burn` | 自分の会員証を焼却（Part4締めの焼却儀式） |

- `deploy`/`mint` はデフォルト `localhost`、`deploy:amoy` 等で Amoy 切替（実装時に確定）。

## 8. 当日の流れと段階設計（時間切れ耐性）

3時間MAX・固定費（開場/バッファ〜20分、Part1座学15分、Part5ディスカッション20分）を引くと、手を動かせるのは約115分。**環境準備を事前課題に追い出し**、当日は面白いところから始める。

### 段階（時間が押したら層3から順に「主催者実演のみ／見るだけ」に降格）
- **Part2**: `docker compose up` で追随勢のチェーン起動＋実演台起動。
- **背骨（必ずやり切る）**: ローカルで `deploy → mint` →「自分のNFTが発行できた」を確認。
- **層2**: `check-membership`（会員判定）＋ `transfer`（隣に送れてしまう実演）→ Part5「だからSoulbound」への布石。
- **層3**: Amoy へ `deploy → mint` → `amoy.polygonscan.com` で確認 → `burn`（焼却儀式）。
- **実演（主催者）は常に先へ進める**。追随勢の完走は待たない。

### Part5（着地・削らない）
- 会員証としての活用（Discordロール／保有確認ログイン）＝ token-gating の議論。
- 「練習台は譲渡できてしまった → 本物は Soulbound」への接続。
